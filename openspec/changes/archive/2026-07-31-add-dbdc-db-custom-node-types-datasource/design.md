## Context

The TencentCloud Terraform Provider already supports several DB Custom (DBDC) data sources (`tencentcloud_dbdc_db_custom_clusters`, `tencentcloud_dbdc_db_custom_nodes`, `tencentcloud_dbdc_db_custom_cluster_nodes`, `tencentcloud_dbdc_db_custom_images`). The `DescribeDBCustomNodeTypes` API in the vendored SDK `tencentcloud-sdk-go/tencentcloud/dbdc/v20201029` lets callers list the node machine types (spec, CPU, memory, disk types, sell status) supported for DB Custom, but no Terraform data source exposes this yet.

Key API facts (verified in `vendor/.../dbdc/v20201029/models.go`):
- Request `DescribeDBCustomNodeTypesRequest` has a single optional field `Filters []*Filter` (supported filter keys: `region`, `zone`, `node-family`, `node-type`).
- Response `DescribeDBCustomNodeTypesResponseParams` has `NodeTypeSet []*DBCustomNodeTypeInfo` plus `RequestId`.
- `DBCustomNodeTypeInfo` fields: `Zone`(*string), `NodeType`(*string), `NodeFamily`(*string), `CPU`(*uint64), `Memory`(*uint64), `Status`(*string), `SystemDiskTypes`([]*string), `DataDiskTypes`([]*string).
- **No pagination** — the request has no `Offset`/`Limit`, so no pagination loop is needed.
- Synchronous API — no async task polling required.

The existing `data_source_tc_dbdc_db_custom_nodes.go` is the closest sibling and is used as the structural template (filters block, `result_output_file`, `helper.BuildToken()` ID, nil-guarded field mapping).

## Goals / Non-Goals

**Goals:**
- Provide a `tencentcloud_dbdc_db_custom_node_types` data source that wraps `DescribeDBCustomNodeTypes` to list supported node machine types.
- Support filtering by `region`, `zone`, `node-family`, `node-type` via the standard `filters` block.
- Follow the established DBDC data source patterns (retry on read, nil-guarded field mapping, `result_output_file`, token-based ID).

**Non-Goals:**
- Not exposing pagination (`Offset`/`Limit`) — the API itself has no pagination.
- Not creating/modifying node types — read-only data source.
- Not adding website docs directly — those are generated by `make doc` in the finalize phase.

## Decisions

### Decision 1: No pagination loop in the service layer
`DescribeDBCustomNodeTypes` has no `Offset`/`Limit` parameters in the SDK request struct, unlike `DescribeDBCustomNodes` / `DescribeDBCustomImages`. Therefore the service helper will be a single-call wrapper (no `for` pagination loop).

- **Rationale**: Matches the actual API surface. Adding a fake pagination loop would be dead code and could mask API errors.
- **Alternative considered**: Reuse the `DescribeDBCustomImagesByFilter` paginated shape — rejected because the request struct lacks the needed fields.

### Decision 2: Service helper signature returns `[]*dbdcv20201029.DBCustomNodeTypeInfo`
Add `DescribeDBCustomNodeTypesByFilter(ctx, param map[string]interface{}) (ret []*dbdcv20201029.DBCustomNodeTypeInfo, totalCount int64, errRet error)` to `service_tencentcloud_dbdc.go`. Since there is no `TotalCount` in the response, `totalCount` is kept in the signature for consistency with sibling helpers but will always be 0 (callers ignore it). The Read in the data source uses its own `resource.Retry(tccommon.ReadRetryTimeout, ...)` wrapper, and the service helper performs a single `ratelimit.Check` + SDK call with the same retry + empty-response guard (`NonRetryableError` when `result == nil || result.Response == nil || result.Response.NodeTypeSet == nil`).

- **Rationale**: Keeps the DBDC service layer uniform with existing helpers while honoring the DATASOURCE empty-response rule (return NonRetryableError, do NOT `d.SetId("")`).
- **Note on retry nesting**: Per the project rule "请不要在retry中再次进行retry", the data source Read wraps the service call in one `resource.Retry`; the service helper itself does NOT add a second nested retry — it only does `ratelimit.Check` + SDK call inside the data-source-level retry callback. (The existing `DescribeDBCustomImagesByFilter` nests a retry inside its loop for pagination; since we have no loop, we avoid that nesting.)

### Decision 3: Filters block mirrors `data_source_tc_dbdc_db_custom_nodes.go`
The `filters` schema is `TypeList` of `schema.Resource` with `name` (Required, string) and `values` (Required, TypeList of TypeString). Filters are translated to `[]*dbdcv20201029.Filter` and placed into `paramMap["Filters"]`, matching the sibling data source.

- **Rationale**: Consistency with existing DBDC data sources; users already know this shape.

### Decision 4: Flatten `NodeTypeSet` directly into `node_type_set`
Per the "列表展开" rule for Describe-style resources, the list is exposed as `node_type_set` (a TypeList of schema.Resource) where each element's fields are flattened (no extra wrapping layer). `SystemDiskTypes` and `DataDiskTypes` are `[]*string` in the SDK and are mapped to `TypeList` of `TypeString` in the schema.

### Decision 5: Data source file naming
Follows the required format: `data_source_tc_dbdc_db_custom_node_types.go` (i.e. `data_source_tc_<Product>_<资源名>.go`).

## Risks / Trade-offs

- [Risk: `totalCount` always 0 in service helper signature] → Acceptable; callers only use `ret`. Keeping the signature parallel to siblings reduces cognitive load. Documented in code.
- [Risk: API returns null `NodeTypeSet` on no matches] → Mitigated by the empty-response rule: service returns `NonRetryableError` with `log.Printf("[DATASOURCE] read empty, skip SetId")`, so state is not silently cleared.
- [Risk: New `DescribeDBCustomNodeTypesByFilter` helper duplicates retry logic] → Mitigated by NOT nesting retry inside the helper; the data source Read owns the single retry wrapper, per the no-nested-retry rule.
- [Risk: Filter key drift] → Filter keys (`region`, `zone`, `node-family`, `node-type`) are taken verbatim from the SDK doc comment; no translation is done, so they match the API exactly.
