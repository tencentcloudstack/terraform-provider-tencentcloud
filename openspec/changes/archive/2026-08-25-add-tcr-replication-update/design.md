## Context

The `tencentcloud_tcr_replication` resource manages TCR (Tencent Container Registry) instance replication rules. Its current implementation in `tencentcloud/services/tcr/resource_tc_tcr_replication.go` defines `Create`, `Read`, and `Delete` methods, but no `Update` method. Every schema field is marked `ForceNew: true`, so any change to a replication rule (description, destination namespace, override flag, filters, or deletion flag) forces Terraform to destroy and recreate the resource.

The TCR API provides a `ModifyReplication` endpoint (already vendored in `tencentcloud-sdk-go/tencentcloud/tcr/v20190924`) that supports in-place modification of a replication rule. The resource's ID is a composite of `sourceRegistryId` and `ruleName` (joined by `tccommon.FILED_SP`), which maps cleanly to the `ModifyReplication` request parameters `SourceRegistryId` and `RuleName`.

The relevant `ModifyReplicationRequest` structure is:

```
SourceRegistryId *string
RuleName         *string
Rule             *ModifyReplicationRule   // { DestNamespace, Override, Deletion, Filters, Enabled }
Description      *string
```

## Goals / Non-Goals

**Goals:**
- Add an `Update` method (`resourceTencentCloudTcrReplicationUpdate`) that calls `ModifyReplicationWithContext` to update a replication rule in place
- Allow in-place updates of `description`, `rule.dest_namespace`, `rule.override`, `rule.filters` (and `filters.type`/`filters.value`), and `rule.deletion` by removing their `ForceNew: true`
- Preserve the composite ID semantics (`sourceRegistryId` + `ruleName`) for Read/Delete/Update

**Non-Goals:**
- Add support for the `Enabled` field in `ModifyReplicationRule` (the resource schema does not currently expose it)
- Make `source_registry_id`, `destination_registry_id`, `rule.name`, `destination_region_id`, or `peer_replication_option` updatable (the API does not support modifying these in place)
- Refactor the existing `Create`/`Read`/`Delete` logic beyond what is necessary to support Update
- Add `website/docs/` documentation manually (generated by `make doc` in the finalization phase)

## Decisions

### Decision 1: Map the composite ID to ModifyReplication's SourceRegistryId + RuleName

The resource ID is `strings.Join([]string{sourceRegistryId, ruleName}, tccommon.FILED_SP)`. In `Update`, we split the ID the same way as `Read`/`Delete` and use `sourceRegistryId` for `SourceRegistryId` and `ruleName` for `RuleName`. This avoids adding new identifier fields and reuses existing ID parsing logic.

**Alternative considered**: Store an explicit server-side rule ID. Rejected — the existing resource already relies on `ruleName` as the identifier, and `ModifyReplication` accepts `RuleName`.

### Decision 2: Remove ForceNew only from fields the API can actually modify

The `ModifyReplication` API accepts `Description` and a `ModifyReplicationRule` with `DestNamespace`, `Override`, `Deletion`, and `Filters`. Therefore we remove `ForceNew: true` from:

- `description`
- `rule` (the outer TypeList, which gates in-place changes to its children)
- `rule.dest_namespace`
- `rule.override`
- `rule.filters` (and its `type`/`value` children)
- `rule.deletion`

Fields that remain `ForceNew: true`:

- `source_registry_id` — identifies the source instance, cannot change via this API
- `destination_registry_id` — not a parameter of `ModifyReplication`
- `rule.name` — serves as `RuleName`, the identifier; changing it means a different rule
- `destination_region_id` — not a parameter of `ModifyReplication`
- `peer_replication_option` (and its children) — cross-account settings, not modifiable via `ModifyReplication`

**Alternative considered**: Keep `rule` as `ForceNew` but selectively allow only `description` updates. Rejected — this would leave the bulk of the rule unmodifiable and fail to meet the requirement of filling in meaningful update logic.

### Decision 3: Reuse the existing retry + logging pattern

The `Update` method follows the same structure as `Create`/`Delete`: build the request, wrap the API call in `resource.Retry(tccommon.WriteRetryTimeout, ...)`, use `tccommon.RetryError(e)` on failure, log via `logId`, and call `resourceTencentCloudTcrReplicationRead` at the end to refresh state.

### Decision 4: Read only the changed/known fields in the Update request

`Update` reads the fields from `d` (the schema data) into the `ModifyReplicationRequest`. Because the diff only contains changed values, we build the request from `d.GetOk`/`helper.InterfacesHeadMap` similar to `Create`, which naturally sends the current desired state of the rule. Sending the full desired rule is acceptable because `ModifyReplication` is an idempotent "set rule to X" style API.

## Risks / Trade-offs

- **[Risk] Removing ForceNew from `rule` could break existing state/import flows** → Mitigation: we keep `rule.name` ForceNew, so the identifier remains stable; existing configurations are unaffected, and in-place update only applies to genuinely modifiable fields.
- **[Risk] `ModifyReplication` does not accept `destination_region_id`/`peer_replication_option`** → Mitigation: these remain `ForceNew`, so any change to them still triggers a clean recreate, matching the previous behavior.
- **[Risk] The API may be eventually consistent after update** → Mitigation: the existing `Read` already retries via `DescribeTcrReplicationById`; calling `Read` after update ensures state converges.
- **[Risk] Unit tests must not require live credentials** → Mitigation: tests use gomonkey to mock the `ModifyReplicationWithContext` call, validating request building and error handling without network access.
