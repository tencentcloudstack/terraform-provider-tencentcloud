## Context

The `tencentcloud_dts_sync_config` resource (`tencentcloud/services/dts/resource_tc_dts_sync_config.go`) manages DTS sync job configuration via the cloud API `ConfigureSyncJob` (write) and `DescribeSyncJobs` (read). The resource's `objects.databases.tables[]` block currently exposes only `table_name`, `new_table_name`, and `filter_condition`, mapping to the `Table` struct fields `TableName`, `NewTableName`, and `FilterCondition`.

The vendored DTS SDK (`github.com/tencentcloud/tencentcloud-sdk-go/tencentcloud/dts/v20211206`) `Table` struct already defines additional fields used by the same two APIs:
- `ColumnMode *string` — whether to sync all columns (`All`) or a subset (`Partial`)
- `Columns []*Column` — column entries, each with `ColumnName` and `NewColumnName`
- `TmpTables []*string` — temporary tables generated by pt-osc/gh-ost to sync
- `TableEditMode *string` — table edit type: `rename` (table mapping) or `pt` (sync attached tables)

These fields are read and written through the identical `Objects.Databases[].Tables[]` JSON path on both APIs, so no SDK upgrade or new API is required. The change is purely a schema + (de)serialization extension within an existing resource.

## Goals / Non-Goals

**Goals:**
- Surface `column_mode`, `columns`, `tmp_tables`, and `table_edit_mode` as optional fields in the `objects.databases.tables[]` block of `tencentcloud_dts_sync_config`.
- Read these fields from `DescribeSyncJobs` and write them to `ConfigureSyncJob` using the existing `Table` struct, preserving the resource's existing Create/Read/Update/Delete flow and retry/state-refresh behavior.
- Keep the change fully backwards compatible: no existing field's type, optionality, or semantics changes.

**Non-Goals:**
- No new DTS resource or data source.
- No changes to the DTS service layer (`service_tencentcloud_dts.go`) beyond what is needed to read/write these fields inside the resource's own CRUD functions.
- No schema changes outside the `objects.databases.tables[]` block.
- No SDK version bump or vendor dependency change.
- No migration of existing state; new fields are optional and absent state simply means "not set".

## Decisions

### Decision 1: Field types and placement within the existing `tables[]` block

All four new fields are added directly inside the existing `objects.databases.tables[]` `schema.Resource` Elem, consistent with the existing sibling fields (`table_name`, `new_table_name`, `filter_condition`).

- `column_mode`: `schema.TypeString`, `Optional`. Mirrors `Table.ColumnMode`.
- `columns`: `schema.TypeList`, `Optional`, Elem is a `schema.Resource` with:
  - `column_name`: `schema.TypeString`, `Optional` → `Column.ColumnName`
  - `new_column_name`: `schema.TypeString`, `Optional` → `Column.NewColumnName`
- `tmp_tables`: `schema.TypeSet`, `Elem: schema.TypeString`, `Optional` → `Table.TmpTables`. Set is chosen for consistency with other list-of-strings fields in this resource (e.g. `functions`, `procedures`, `triggers`, `events`).
- `table_edit_mode`: `schema.TypeString`, `Optional`. Mirrors `Table.TableEditMode`.

**Rationale**: These are all `Optional` because the cloud API marks them `omitnil` and the existing resource pattern uses Optional for every field in this block. `tmp_tables` uses `TypeSet` to match the established convention for string collections elsewhere in the same `Database` Elem. `columns` uses `TypeList` (not `TypeSet`) because column order is meaningful and each entry is a structured object, matching the resource's treatment of other structured sub-lists (`ddl_options`, `views`).

### Decision 2: Read path nil-guarding

In `resourceTencentCloudDtsSyncConfigRead`, each new field is only set when the corresponding `Table` field is non-nil (and for list-valued fields, non-empty), following the same nil-check pattern already used for `tables.TableName`, `tables.NewTableName`, and `tables.FilterCondition`. This prevents writing empty structures into state and keeps the behavior consistent with the rest of the read function.

For `Columns`, the read loop only copies `ColumnName` / `NewColumnName` when they are non-nil, mirroring the existing handling of `views.ViewName` / `views.NewViewName`.

### Decision 3: Write path field assignment

In `resourceTencentCloudDtsSyncConfigUpdate`, inside the existing `for _, item := range v.([]interface{})` loop that builds each `dts.Table`, the new fields are assigned after `FilterCondition`:
- `column_mode` → `table.ColumnMode = helper.String(v.(string))`
- `columns` → iterate the list, build `dts.Column` entries with `ColumnName`/`NewColumnName`, append to `table.Columns`
- `tmp_tables` → convert the `*schema.Set` to `[]*string` via the existing `helper.StringsInterfaces` / append pattern used for `functions`, `procedures`, etc.
- `table_edit_mode` → `table.TableEditMode = helper.String(v.(string))`

No new retry logic is introduced; the existing `resource.Retry(tccommon.WriteRetryTimeout, ...)` around `ConfigureSyncJob` and the subsequent `WaitForState` remain unchanged.

### Decision 4: Documentation and tests

- The `resource_tc_dts_sync_config.md` example is updated to show the new fields (using `jsonencode` only if a JSON-string field appears; here all fields are native Terraform types, so plain HCL is used).
- `website/docs/r/dts_sync_config.html.markdown` is regenerated via `make doc` in the finalize phase, not edited manually.
- Unit tests in `resource_tc_dts_sync_config_test.go` are extended to cover the new fields, mocking the DTS API with gomonkey (consistent with the project rule for new fields on existing resources — actually this resource predates the rule, so the existing test style is followed and extended).

## Risks / Trade-offs

- **Risk**: `ColumnMode` on `ConfigureSyncJob` does not support `Partial` (per the SDK comment: "ModifySyncJobConfig接口里的对应字段ColumnMode暂不支持Partial"). → **Mitigation**: The Terraform schema still exposes `column_mode` as a free string (matching the cloud API's string type) and does not validate the enum client-side, deferring to the cloud API for validation. The spec does not promise `Partial` works on write; it only promises the configured value is forwarded. This matches how the existing schema handles other enum-like string fields (e.g. `table_mode`, `view_mode`).
- **Risk**: `TmpTables` and `NewTableName` are mutually exclusive at the cloud API level, and `TmpTables` is only meaningful when `TableEditMode == "pt"`. → **Mitigation**: This is a cloud-API-level constraint, not enforced by the provider. The schema exposes all fields independently (consistent with the SDK's `Table` struct and the existing `new_table_name` field), and the cloud API returns an error if the combination is invalid. The spec/scenarios do not promise cross-field validation.
- **Trade-off**: Using `TypeList` for `columns` means order matters in state, but since column ordering is meaningful for reproducible configs, this is acceptable and matches the resource's convention for structured sub-lists.
